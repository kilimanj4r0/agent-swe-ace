# Skillbook Injection Procedure

## Overview

Skillbook skills are injected into the mini-swe-agent's instance template (the main instruction sent to the LLM for each turn). The injection happens at predict phase via `build_instance_template()` in `src/phases/predict.py`.

## Agent Instruction Structure

The mini-swe-agent uses a single instance template (~154 lines) that serves as the system-level instruction. No separate system/user message split — it's all one template with Jinja2 placeholders.

```
<pr_description>
Consider the following PR description:
{{task}}                          ← filled with instance's problem_statement
</pr_description>

<instructions>
# Task Instructions

## Overview
You're a software engineer interacting continuously with a computer...
(many instruction lines)

## Command Execution Rules
(format requirements, bash block rules, etc.)

**CRITICAL REQUIREMENTS:**
- EXACTLY ONE bash code block per response
- ...

Example of a CORRECT response:
<example_response>
...                              ← SKILLBOOK INJECTED HERE (line 68)
</example_response>

(more example responses)

...submit instructions...
</instructions>
```

**Injection point:** The skillbook section is inserted **immediately before `<example_response>`** (line 69). This places it between the command rules and the response examples — the agent sees skills before seeing how to format responses.

## Which Fields Are Injected

From the 5 fields stored per skill in `skillbook.json`:

| Field | Injected? | Format |
|---|---|---|
| `id` | Yes | `### <id>` (markdown heading) |
| `content` | Yes | Body text after heading |
| `justification` | Conditional | `**Why this helps:** <justification>` (only if non-null) |
| `evidence` | **No** | Ignored — never sent to agent |
| `section` | **No** | Used only for deduplication grouping |

## Injection Format

The `wrap_skillbook_context()` function formats each skill, then `build_instance_template()` wraps them in a section:

```markdown
## Learned Strategies (Skillbook)

These are strategies learned from previous attempts. Use them to guide your approach:

### code_fixing-00001

Identify the exact line containing 'return s.replace(".[", "[")' in pytest's python.py file...

### shell_commands-00002

Avoid shell escaping issues by using a different delimiter in sed commands...

### file_modification-00007

VERIFIED: The specific line to modify is line 272 in django/contrib/admin/options.py

**Why this helps:** Exact line was found and verified with grep -n "empty_label.*None".

⚠️ **CRITICAL REMINDERS:**
1. These skills describe approaches, NOT complete solutions. You MUST implement actual code changes.
2. Do NOT put multiple bash commands in one response - use ONE command per response.
3. Before submitting, verify your patch exists with: `git diff --cached`
4. If you think you've "successfully implemented" but git diff is empty, you haven't actually edited any files.
5. The source code in /testbed IS writable - do not claim you "cannot modify installed packages".

When you apply a strategy successfully, reference it with [skill-id] notation in your reasoning.
```

## Default ACE Skills vs Custom SWE Skills

### Default ACE (custom_swe_learn: false)

Generated by ACE's default `Reflector` + `SkillManager`. Skills tend to be instance-specific, shorter, no type prefixes.

Example skillbook entry:
```json
{
  "code_fixing-00001": {
    "id": "code_fixing-00001",
    "section": "code_fixing",
    "content": "Identify the exact line containing 'return s.replace(\".[\", \"[\")' in pytest's python.py file and modify it to handle edge cases",
    "justification": null,
    "evidence": null
  },
  "shell_commands-00002": {
    "id": "shell_commands-00002",
    "section": "shell_commands",
    "content": "Avoid shell escaping issues by using a different delimiter in sed commands",
    "justification": null,
    "evidence": null
  },
  "text_processing-00003": {
    "id": "text_processing-00003",
    "section": "text_processing",
    "content": "Use Python scripts for complex text replacements when shell escaping is problematic",
    "justification": null,
    "evidence": null
  }
}
```

Characteristics:
- Sections: `code_fixing`, `shell_commands`, `text_processing`, `debugging`, etc.
- `justification` and `evidence` are often `null` (30% populated in default mode)
- 84 skills in a typical Verified per-repo run (django: 991)

### Custom SWE (custom_swe_learn: true)

Generated by `SWEReflector` + `SWESkillManager`. Uses type prefixes (`AVOID:`, `VERIFIED:`, `CONSIDER:`), more structured, includes justification/evidence.

Example skillbook entries:
```json
{
  "file_modification-00003": {
    "id": "file_modification-00003",
    "section": "file_modification",
    "content": "AVOID: Executing multiple commands in one response leading to format errors",
    "justification": null,
    "evidence": null
  },
  "environment-00005": {
    "id": "environment-00005",
    "section": "environment",
    "content": "VERIFIED: Use /testbed directory for file modifications (writable in Docker)",
    "justification": "Confirmed that /testbed is writable and contains the source code, allowing for necessary edits.",
    "evidence": null
  },
  "file_location-00006": {
    "id": "file_location-00006",
    "section": "file_location",
    "content": "VERIFIED: The actual file to modify is /testbed/django/db/models/fields/__init__.py",
    "justification": "Provides accurate guidance on where to make the fix for the Django issue.",
    "evidence": "Agent found the relevant code section and correctly identified the problem location"
  },
  "fix_implementation-00008": {
    "id": "fix_implementation-00008",
    "section": "fix_implementation",
    "content": "CONSIDER: The fix requires replacing apps.get_models(app_label) with apps.get_app_config(app_label).get_models() in makemigrations.py",
    "justification": null,
    "evidence": null
  }
}
```

Characteristics:
- Type prefixes: `AVOID:` (anti-patterns), `VERIFIED:` (confirmed working), `CONSIDER:` (suggestions)
- Sections: `file_modification`, `environment`, `file_location`, `fix_implementation`, `debugging`, etc.
- `justification` and `evidence` populated more often than default (19% populated in SWE mode)
- 1142 skills in a typical Verified per-repo run (django: 1142)
- ~10-30% more skills than default ACE per repo

## Why Are `justification` and `evidence` Often Null?

Both fields are **supported by design** in both modes. The pipeline is:

1. **Reflector** extracts learnings with `evidence` and `justification` on `ExtractedLearning` (ACE default) or on `AntiPattern`/`Discovery`/`UnvalidatedHypothesis` (SWE mode)
2. **SkillManager** prompt explicitly requests them in the output JSON schema:
   ```json
   "justification": "<why this improves skillbook>",
   "evidence": "<specific detail from reflection>"
   ```
3. **Skillbook.apply_update()** passes them through to `Skill(justification=..., evidence=...)`

But they're **optional fields** (default `""` or `None`) in both the prompt schema and the output models. The LLM treats them as optional and only populates them when it has strong, specific evidence.

### Population Rates (Verified dataset, django repo)

| Mode | Total Skills | Has `justification` | Has `evidence` | Both |
|---|---|---|---|---|
| Default ACE | 84 | 25 (30%) | 25 (30%) | 25 (30%) |
| Custom SWE | 1142 | 213 (19%) | 203 (18%) | 203 (18%) |

Default mode has a higher rate (30% vs 19%) likely because the default SkillManager processes fewer learnings per call and has more capacity to fill optional fields. The SWE SkillManager generates many more skills per reflection, filling `justification`/`evidence` selectively — typically for `VERIFIED:` discoveries and anti-patterns with clear failure evidence.

### Example with justification/evidence (default mode)
```json
{
  "debugging-00006": {
    "section": "debugging",
    "content": "In pytest-xdist, exception chain information is lost during serialization...",
    "justification": "This directly addresses the core issue identified in the reflection where exception...",
    "evidence": "Multiple analyses confirmed that _to_json method in src/_pytest/reports.py doesn..."
  }
}
```

### Example with justification/evidence (SWE mode)
```json
{
  "file_location-00006": {
    "section": "file_location",
    "content": "VERIFIED: The actual file to modify is /testbed/django/db/models/fields/__init__.py",
    "justification": "Provides accurate guidance on where to make the fix for the Django issue.",
    "evidence": "Agent found the relevant code section and correctly identified the problem location"
  }
}
```

**Bottom line:** This is not a bug. The LLM conservatively fills these fields only when it has concrete evidence from the trajectory. Most skills are generic enough that the LLM doesn't produce specific justification/evidence for them.

## Code Path

```
ExperimentLoop.run_instance()
  → PredictPhase.run(instance, skillbook, ...)
    → MiniSWEAgent.run(instance, skillbook)
      → build_instance_template(skillbook)        # src/phases/predict.py:233
        → wrap_skillbook_context(skillbook)        # src/phases/predict.py:203
        → inject before <example_response>         # src/phases/predict.py:289
      → agent runs with modified template
```

## Scaling Concerns

With 1142 skills (SWE django run), the skillbook section alone can be ~100K+ tokens. This inflates the instance template significantly, consuming context window space and contributing to format error loops (agent cites skill IDs instead of writing code).

Fields `evidence` and `section` are NOT injected, so they don't contribute to context usage — they exist only for deduplication and internal tracking.
